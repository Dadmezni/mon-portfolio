Construire le CRUD

 
    
  
  1. Le modèle Eloquent
    Pourquoi : $fillable liste les champs que l’on peut remplir en masse ; tout le reste est refusé, ce qui protège contre l’injection de champs (mass assignment). Le cast garantit un prix toujours formaté.
    class Product extends Model
{
    use HasFactory;

    protected $fillable = ['name', 'description', 'price'];

    protected function casts(): array
    {
        return ['price' => 'decimal:2'];
    }
}
    2. 
  
  2. Factory et seeder : des données de démonstration
    Pourquoi : une factory fabrique des données réalistes, reproductibles, sans rien saisir à la main.
    public function definition(): array
{
    return [
        'name' => fake()->words(3, true),
        'description' => fake()->sentence(),
        'price' => fake()->randomFloat(2, 5, 500),
    ];
}
    # dans DatabaseSeeder::run() : Product::factory()->count(20)->create();

php artisan tinker

    Attention : migrate:fresh --seed efface toutes les tables. Jamais en production.

    4. 
  
  4. Le contrôleur
    Pourquoi : il orchestre seulement : il reçoit des données déjà validées (validated()), appelle le modèle, puis redirige. paginate() évite de charger toute la table. Importez les classes utilisées (l’éditeur propose l’import automatique).
    public function index()
{
    return view('products.index', [
        'products' => Product::latest()->paginate(10),
    ]);
}

public function store(ProductRequest $request)
{
    Product::create($request->validated());
    return back()->with('ok', 'Produit créé.');
}

public function update(ProductRequest $request, Product $product)
{
    $product->update($request->validated());
    return back()->with('ok', 'Produit modifié.');
}

public function destroy(Product $product)
{
    $product->delete();
    return back()->with('ok', 'Produit supprimé.');
}
    Le route model binding transforme l’identifiant de l’URL en objet $product, avec une erreur 404 automatique s’il n’existe pas.

  3. Éviter le problème N+1
    Pourquoi : afficher la catégorie de 10 produits sans précharge déclenche 1 requête pour la liste + 10 pour les catégories. with() les regroupe en 2 requêtes.

Image de production (Render)

 
Render fournit la variable PORT ; Apache doit y écouter et servir public/. Ce Dockerfile utilise deux étages pour une image plus légère.

 
FROM composer:2 AS vendor
WORKDIR /app
COPY composer.* ./
RUN composer install --no-dev --no-scripts --prefer-dist --no-interaction
COPY . .
RUN composer dump-autoload --optimize --no-dev

FROM php:8.3-apache
RUN apt-get update && apt-get install -y --no-install-recommends libpq-dev \
    && docker-php-ext-install pdo_pgsql opcache \
    && a2enmod rewrite \
    && rm -rf /var/lib/apt/lists/*
ENV APACHE_DOCUMENT_ROOT=/var/www/html/public
RUN sed -ri 's!/var/www/html!${APACHE_DOCUMENT_ROOT}!g' /etc/apache2/sites-available/*.conf
WORKDIR /var/www/html
COPY --from=vendor /app .
RUN chown -R www-data:www-data storage bootstrap/cache
CMD ["sh","-c","sed -i \"s/80/${PORT:-10000}/\" /etc/apache2/ports.conf /etc/apache2/sites-available/000-default.conf && apache2-foreground"]

 
Adaptez et testez ce modèle localement avec docker build -f Dockerfile.prod . avant de déployer.

 






 
5Git et GitHub

 
⏱ 25 minBranchesPull Request

 
Chaque changement devient une étape lisible, partageable et réversible.

 
Pas à pas

 
    
  
  1. Vérifier ce que Git ignore, avant le premier commit
    Pourquoi : un secret commité reste dans l’historique même après suppression. On vérifie donc avant, pas après.
    git init
git check-ignore -v .env vendor
    Résultat attendu : deux lignes montrant la règle de .gitignore qui ignore chaque chemin. Si rien ne s’affiche, ne commitez pas encore.
    2. 
  
  2. Premier commit et premier push
    Utilisez les commandes du bloc « premier envoi » ci-dessous.
    Résultat attendu : le code est visible sur GitHub, sans .env ni vendor/.
    3. 
  
  3. Travailler en branche, par petits commits
    Pourquoi : main reste toujours déployable. git add -p permet de choisir précisément ce qui entre dans le commit. Adoptez une convention de message : feat: nouvelle fonction, fix: correction, docs: documentation, test: tests.
    git switch -c feature/categories
git add -p
git commit -m 'feat: add categories relation'
git push -u origin feature/categories
    4. 
  
  4. Ouvrir et relire la Pull Request
    Sur GitHub, cliquez Compare & pull request. Décrivez : le pourquoi, ce qui change, comment tester. Relisez le diff vous-même avant de demander une revue. Fusionnez seulement quand la CI est verte.
    git switch main
git pull
git branch -d feature/categories
    5. 
  
  5. Corriger une erreur sans casser l’historique
    Pourquoi : sur une branche partagée, on n’efface pas : on ajoute un commit qui annule.
    git restore fichier.php        # abandonne les changements non commités
git revert abc1234             # annule un commit déjà partagé
git log --oneline --graph      # relit l’historique
    Évitez : git push --force sur main et reset --hard sur du travail partagé.
    6.

git add .
git commit -m "Initialise le catalogue Laravel"

git remote add origin https://github.com/VOTRE-COMPTE/devops-catalogue.git

  • Commits courts, message décrivant le résultat.
  • Relire git status avant chaque commit.
  • .env et clés privées sont ignorés par Git.
  • La Pull Request décrit le but et les tests.

 
Secret poussé ? Le supprimer ne suffit pas : l’historique le garde. Révoquez-le d’abord, puis traitez l’historique.

8Projet de synthèse

 
⏱ 3 hLivrable noté

 
Assembler le tout dans un catalogue de produits déployé.

 
Pas à pas

 
    
  
  1. Planifier avant de coder
    Créez une issue GitHub par fonctionnalité : CRUD, validation, catégories, recherche, déploiement. Une issue = une branche = une Pull Request.
    2. 
  
  2. Construire par tranches verticales
    Pourquoi : chaque tranche (base, modèle, contrôleur, vue, test) est démontrable et déployable seule, ce qui réduit les risques.
    Ordre conseillé : 1. CRUD produits → 2. validation → 3. catégories → 4. recherche → 5. protection des routes → 6. déploiement.
    3. 
  
  3. Garder la CI verte à chaque fusion
    Aucune Pull Request n’est fusionnée avec un test rouge. Chaque fonction apporte au moins un test.
    4. 
  
  4. Déployer, puis faire un test de fumée
    curl -i https://VOTRE-SERVICE.onrender.com/up
curl -i https://VOTRE-SERVICE.onrender.com/health
curl -s https://VOTRE-SERVICE.onrender.com/api/products
    Résultat attendu : codes 200 et un JSON valide. Créez ensuite un produit depuis l’interface et retrouvez-le après un nouveau déploiement.
    5. 
  
  5. Rédiger le README
    # Catalogue DevOps
## Présentation
